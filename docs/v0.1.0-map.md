# lobotomy v0.1.0 map

*Wayfinder map, 2026-10-26. It plans and builds nothing. Each question for Jake in [section 4](#4-open-questions) has a recommended answer he can just say yes to.*

## 1. Destination

v0.1.0 is the version Jake posts. Qwen3-0.6B talks on the Coralboard's 1-watt NPU, and a 3D map in the Mac's browser lights up all 86,016 of its neurons for every word. Hover over a neuron to read what it does. Drag its slider and the answer bends on the next word. The scope is Lyra's explorer (atlas, live glow, steering), done deeper. The atlas is built on a faithful copy of the exact 4-bit graph the chip runs. A neuron only counts as real if it beats random pushes of the same size, with false discoveries held to 5% across all 86,016. Labels must beat random labels, effects carry error bars, and every slider stops before the text breaks. We show that the board matches its copy, and we publish what glowing costs in speed and joules. Every colour, size and glow on screen stands for a number. A Blender clip rendered from a real recorded session leads the post.

**Not in v0.1.0:** a Claude chat agent like Lyra's, the multiply/ablate mode, thinking mode, other models.

Mapping turned up facts that change how T4, T6, T7 and T8 should be done (details and sources in [Appendix C](#appendix-c-findings-for-v001)):
1. The runtime hands the NPU at most 64 buffers per call, and Qwen already uses about 59. So the glow must be **one** `[28, 3072]` output, not 28.
2. torq-examples' runner treats every output after the first as a KV cache. An extra output needs a small runner change.
3. Synaptics changed the default KV-cache layout on 2026-10-23 (8.5 vs 6.0 tok/s on SL2610). The published v2.3.0 files use the old layout.
4. T5's parity sequences are 58–82 tokens long. If the chip rounds RoPE angles to bf16 (unverified), the damage shows mainly after position ~128 (P4), so T7 needs long sequences too.

### R1. Steering and glow fit through the chip's I/O
- **Question:** Can Torq compile Qwen with one glow output (all 86,016 values) and one steering input `A[28, 3072]`, added to each layer's neurons just before `down_proj`, within the runtime's limit of 64 bindings and without slowing the NPU program?
- **Why risky:** A *binding* is one buffer handed to the NPU program. The runtime caps bindings at 64 per call, and Qwen already uses about 59 (30 inputs, 29 outputs, per the model card). The add sits inside the MLP, which the compiler computes as one fused pass, so it may split kernels or lose the prefetch schedule that hides compute behind weight loads. If this fails, the sliders can't run on the chip.
- **Cheapest experiment:** Run `torq-export-model qwen -s qwen3-0.6b --skip-torq` to get the ONNX graph. Use onnx_graphsurgeon to add one concatenated output and one input `A`, with row `l` added before layer `l`'s `down_proj`. Compile with the stock flags plus `--torq-enable-profiling`. Count bindings with `torq-lab inspect`, and compare the compile-time cycle and DMA estimates with the glow-only build. Then run one decode step in the x86 simulator, once with `A = 0` and once with one neuron dosed.
- **Runs on:** RunPod CPU, then the board for timing. **Cost:** 2–3 pod-hours, about $1 (CPU pod price unverified). **Blocked by:** T4. The board part also needs T3 and T6.
- **Pass:** ≤ 64 bindings. With `A = 0`, the logits are bit-identical to the glow-only build (adding zero is exact in bf16). A one-neuron dose moves the residual by the intended vector (cosine ≥ 0.99 against the replica's change). Compile-time cycles stay within 1% of the glow-only build. On the board, a slider change shows on the next token.

### R2. The board matches the replica on the next token
- **Question:** Fed the same tokens, does the board pick the same next token as our INT4 replica ≥ 99% of the time, with every layer's cosine ≥ 0.99? What must the replica copy from the chip's arithmetic to get there?
- **Why risky:** The LM head outputs bf16, so logits near 20 sit 0.125 apart, and T5 found exact ties in 7 of 134 greedy steps. Our probes ([Appendix B](#appendix-b-probes-run-for-this-map)) show that bf16 rounding alone flips 1.65% of next-token picks against fp32, all of them near-ties. Rounding only the rotary position angle (RoPE) to bf16 drops agreement to 94.7% and layer cosine to 0.985 at positions 192–249. The chip computes sigmoid (and so SiLU), reciprocal and sin/cos with lookup tables, and it adds up reductions in fp32. T5 copies the chip's INT4 matmul kernel but runs the rest as Hugging Face's bf16 Qwen3, which computes RoPE angles in fp32. A replica that ignores these details will probably miss 99%. The cosine bar works as a test: bf16 noise gives 0.9997 and fp32-vs-INT4 gives 0.94–0.99, so ≥ 0.99 means "matches the replica", not "matches fp32".
- **Cheapest experiment:** Fix a parity set spanning positions 0–255: 40 sequences, ≥ 2,000 scored positions, plus 10 steered settings. Build the replica up in steps:
  1. T5's `npu` mode: the chip's INT4 kernel, bf16 elsewhere.
  2. Plus the RoPE dtype path, read from the converted ONNX.
  3. Plus the compiler's sigmoid, reciprocal and sin/cos tables (Apache-2.0 source).
  4. Plus fp32 sums for reductions.

  Compare each step with the simulator op by op (R5), then with the board through the glow output. Sort the misses by top-2 margin and by position, and report cosine with and without position 0. Check the compile log for which matmul kernel each layer got: T5 notes a fallback when tiling doesn't split evenly.
- **Runs on:** the board and cloud CPU. **Cost:** free. **Blocked by:** T5 and T7, plus R5 for the per-op diagnosis.
- **Pass:** top-1 ≥ 99% and cosine ≥ 0.99 on all 28 layers, in every position bucket, unsteered and steered. If every miss is a near-tie, see Q1.

### R3. Enough neurons survive FDR
- **Question:** Against random directions drawn from each layer's `W_down` column space and pushed by the same amount, how many neurons in two pilot layers survive Benjamini–Hochberg at q = 0.05, scaled to all 86,016? Is the list stable?
- **Why risky:** A fair null removes the easy wins. In our probe (P5), the column-space nulls match real neurons' average disruption, with an AUC of 0.52–0.55, where 0.5 means indistinguishable. Lyra-style isotropic nulls are off in opposite directions at L8 and L19 (AUC 0.68 and 0.33), so her 19.6% "beats every control" doesn't carry over. Real neurons stand apart only in the tail: on cross-fitted lift, 22–25% of real pushes beat the null's 95th percentile, against the 5% expected by chance. And with N nulls per layer the smallest possible p-value is 1/(N+1). With 2,048 nulls, BH rejects nothing unless at least 840 neurons sit at that floor.
- **Cheapest experiment:** On one RTX 4090, take layers 8 and 19: all 3,072 neurons × 2 signs plus 2,048 column-space nulls each. Run the pre-registered statistic ([Appendix D](#appendix-d-atlas-recipe)) on 16 contexts × 64 tokens. Compute empirical p-values (Phipson–Smyth) and BH with m = 86,016. Repeat on a second, disjoint set of contexts. Time the run for the budget, and check the GPU replica against T5's CPU replica.
- **Runs on:** RunPod GPU. **Cost:** about 42M token-passes for both context sets, 20–40 minutes, about $1. **Blocked by:** T5 (the CPU replica it is checked against). Not by the board.
- **Pass:** at least one survivor in each pilot layer at the scaled threshold, ≥ 70% overlap of the top-200 survivors across the two context sets, and GPU-vs-CPU replica cosine ≥ 0.999 on every layer.

### R4. A stranger can see the label in a steered answer
- **Question:** Shown a neuron's label and two answers to the same prompt, does a stranger pick the one pushed by that neuron at least 70% of the time? The other answer is pushed by a random direction of the same size, with the same sampling seed.
- **Why risky:** Any push changes greedy text 83–98% of the time (Lyra), so the foil must be a random push, not the plain answer. Safe doses are small: our ocean neuron (L8 n908) reads well at +0.5, drifts at +1 and breaks at +2. A label may also describe what the neuron reads when the push shows what it writes.
- **Cheapest experiment:** First a proxy: 100 trials over 25 survivors at their safe dose, judged by Claude Haiku 5.5. Then 10 trials with one real stranger, to check the proxy.
- **Runs on:** RunPod GPU (the replica) for the pilot; the board for the final test. **Cost:** under $1 of API, plus people's time. **Blocked by:** R3, R6 and R8. The final run also needs R1 and R2.
- **Pass:** the proxy scores ≥ 80%, because a true rate of 75% clears 70% at n = 50 only 84% of the time. Final: ≥ 70% at n ≥ 50.

### R5. The Torq simulator as the middle rung
- **Question:** Can the x86 simulator (`torq_hw_type=sim`, a C model of the NPU) run our compiled Qwen fast enough to compare with the board and the replica? Does it match the board bit for bit?
- **Why risky:** Synaptics doesn't document its speed, and their docs call the part that runs on the cycle simulator "by far the slowest". If one token takes hours, this rung shrinks to single layers.
- **Cheapest experiment:** Time one decode step of the stock graph compiled for the simulator. If it takes more than 10 minutes, cut out one decoder layer as an ONNX subgraph and simulate only that. Then feed the board the same inputs.
- **Runs on:** RunPod CPU. **Cost:** 1–4 pod-hours, about $1–2. **Blocked by:** T4. The board comparison also needs T3.
- **Pass:** we have a time per token, the simulator and the board agree exactly, or within one bf16 step for ops that fall back to the CPU, on ≥ 3 positions or one full layer, and we know which replica variant is closest to the simulator for each op.

### R6. Claude labels beat random labels
- **Question:** Do labels Claude writes from top-activating examples plus the logit and steer lenses beat shuffled labels in simulation scoring on held-out text? Which Claude model is worth the money?
- **Why risky:** MLP neurons are polysemantic, meaning one neuron responds to several unrelated things. Anthropic found 100 random MLP neurons much harder to interpret than 100 random SAE features, which are directions found by a sparse autoencoder (Templeton et al. 2024). OpenAI found a token lookup table beat GPT-4's explanations on random text (Bills et al. 2023). Claude's API returns no token log-probabilities (unverified; check the docs), so the simulator must write whole-number guesses, as Transluce's does. That is noisier than Bills' expected-value method. Each Qwen neuron also has two signed *poles*, and each pole needs its own label.
- **Cheapest experiment:** Take 300 neuron-poles from the R3 pilot: 150 survivors and 150 random. Label them with Haiku 5.5 and with Sonnet 5.5. Simulate with Haiku 5.5 on 10 held-out top-activating and 10 random excerpts of 64 tokens. Score each with Pearson r. The baseline is a label taken from another neuron in the same layer. Also compute Bills' token-lookup baseline.
- **Runs on:** cloud CPU plus the Claude Batch API. **Cost:** about $3–5. **Blocked by:** R3's activation pass. It could start earlier on random neurons from the CPU replica.
- **Pass:** the mean real-minus-shuffled score is above 0, with a 95% bootstrap CI that excludes 0. Choose the cheapest model whose score falls within the CI of the best.

### R7. Glow and steering cost at most 3% tok/s
- **Question:** Does streaming all 86,016 values per token, plus the steering input, cost ≤ 3% tok/s end to end, as the bytes-per-token roofline predicts?
- **Roofline:** A decode step streams about 323 MB (the compiler's estimate of the NPU's memory transfers, called DMA, for the read-only KV layout) in about 102 ms, which works out to 3.2 GB/s.
  - The glow output is 28 × 3,072 × 2 B = 172 KB, or 0.05% of those bytes: about 0.05 ms of the 118 ms token.
  - The steering input adds another 172 KB of NPU reads. The host only re-uploads it when a slider moves.
  - On the host, Python on two Cortex-A55 cores has to copy the values out, convert bf16 to the float16 frames of T2's protocol and serve them over long-poll HTTP. That is roughly 1–3 ms per token (estimate), or 1–2.5%, unless it overlaps with the next NPU call. **The host side is the real risk.**
- **Why risky:** host-side Python, a broken fusion (R1) or per-output runtime overhead could cost 10× the NPU-side estimate.
- **Measurement plan:**
  - **Compile time first:** DMA bytes and cycles from `--torq-enable-profiling` for three builds (stock, +glow, +glow+steer). This runs on RunPod and needs no board.
  - **Then the board:** the same three builds × 5 interleaved runs × 200 decode tokens, with the NPU pinned to max frequency through devfreq. Record tok/s, NPU time from `/sys/class/misc/torq/statistics/torq_inference_time`, and CPU %. Measure once with the graph alone (like `profile.py`) and once end to end with the browser connected.
  - Report the mean slowdown with a 95% CI.
- **Runs on:** RunPod CPU and the board. **Cost:** free plus about one pod-hour. **Blocked by:** T6 (glow build), R1 (steer build) and T8 (server).
- **Pass:** the upper 95% bound of the end-to-end slowdown is ≤ 3% for the glow output (E2). The steering input is reported the same way, also targeting ≤ 3%.

### R8. A safe range for every slider
- **Question:** Can a cheap teacher-forced signal (KL along a 5-step dose ladder) predict, for each neuron and sign, the dose where generations stop making sense?
- **Why risky:** The cliff differs by neuron and layer. In our CPU demo, L8 n908 was fine at +0.5, odd at +1 and garbage at +2. In Lyra's runs, relative doses broke the early layers: 92% of outputs were empty at L0, +0.8. A bad proxy gives sliders that break the text or stop too early.
- **Cheapest experiment:** Take 100 neurons spread evenly across layers. Generate at doses ±{0.25, 0.5, 1, 1.5, 2, 3}, with 3 seeds on 2 prompts. Judge each sample coherent or broken with Haiku 5.5, plus two metrics: the unsteered model's log-prob per token, and distinct-2 (the share of unique word pairs). Fit the KL threshold κ that best predicts the judged cliff.
- **Runs on:** RunPod GPU alongside R3, or cloud CPU (100 neurons is small). **Cost:** under $1 of GPU plus under $1 of API. **Blocked by:** T5.
- **Pass:** the KL-based cliff falls within one ladder step of the judged cliff for ≥ 80% of neuron-signs.

### R9. A layout that groups neurons by meaning
- **Question:** Does a co-activation layout put neurons with similar labels closer together than a `W_down`-UMAP layout like Lyra's? In it, x is the layer and y/z come from which neurons fire together on real text.
- **Why risky:** Lyra measured her `W_down` layout as grouping only weakly: neighbour recall of 4.7% vs 1.0% for index order at L8, and 12.9% vs 0.7% at L22. Co-activation needs many tokens and enough labels to score. Fixing one axis to the layer may also squash structure that crosses layers.
- **Cheapest experiment:** From R3's activation pass, take 16k sampled positions × 86,016 neurons (fp16, 2.8 GB). Standardize, keep the 64 main directions with PCA (one basis shared by all layers), then UMAP to 2D. The baseline is a per-layer UMAP of normalized `W_down` columns. Score it first without labels: how well do a neuron's 10 nearest neighbours co-activate on held-out text? Once R6's labels exist, score neighbour-label agreement: the cosine between bge-small embeddings of a neuron's label and its 10 neighbours' labels, minus the same for random pairs.
- **Runs on:** RunPod GPU (activations) and cloud CPU (UMAP). **Cost:** about $1. **Blocked by:** R3's activation pass. Label scoring needs R6.
- **Pass:** the co-activation layout beats `W_down` UMAP on neighbour-label agreement, with a paired 95% bootstrap CI that excludes 0.

### R10. Error bars tight enough to rank effects
- **Question:** With 4 held-out prompts × 5 sampled seeds, are the 95% CIs on KL and concept-logprob lift narrow enough to rank survivors?
- **Why risky:** Sampled text is noisy, and a label's concept tokens can be rare.
- **Cheapest experiment:** Take 100 labelled survivors from R6. Sample 4 prompts × 5 seeds at the test dose on the replica. Bootstrap over prompt-seed pairs, and check how the CI width shrinks with more seeds.
- **Runs on:** RunPod GPU. **Cost:** under $1. **Blocked by:** R6.
- **Pass:** for ≥ 80% of survivors, the CI half-width is under half the effect. If not, add seeds; the cost grows linearly and the budget has room.

### R11. 60 fps on the MacBook Air
- **Question:** Does a three.js WebGPU + TSL scene hold 60 fps on Jake's MacBook Air in Chrome (Safari dropped: Jake doesn't use it, 2026-10-28)? The scene has 86,016 instanced sprites, one texture upload per token, decay trails from a compute pass, and bloom.
- **Why risky:** We don't know the chip (M1 to M4). Safari 26 is the first Safari with WebGPU on by default. Bloom adds full-screen passes at Retina resolution, and overlapping additive sprites cost more when zoomed in. The sprites themselves are light: three.js's own compute example runs 200,000 particles.
- **Cheapest experiment:** A ~150-line benchmark page fed fake activations at 8 tok/s.
  - Each token uploads one 3,072 × 28 half-float texture (172 KB, T2's frame format).
  - A compute pass keeps `glow = max(glow · e^(−dt/τ), new)`.
  - The page logs frame intervals for 60 s at native resolution and posts them back.
  - Sweep bloom resolution (1× and 0.5×) and sprite size.
- **Proposed channel table (for I6 and the UI grill):**

  | Channel | Data |
  |---|---|
  | x | layer, 0–27 |
  | y, z | co-activation embedding (R9) |
  | brightness | current activation ÷ that neuron's p99 \|activation\| (T2's calibration) |
  | hue | sign: warm = positive pole, cool = negative pole |
  | saturation | atlas status: colour = FDR survivor, grey = not shown as real |
  | size | effect size (KL at dose 0.5) |
  | trail | recency: glow decays with a half-life of a few tokens |
  | bloom | only where brightness > 1 (above p99) |
  | ring | neuron is being steered; radius = dose |

- **Runs on:** Jake's Mac. It can't be any of the four usual places: the check is about this laptop, and the cloud sandbox has no GPU. **Cost:** free; Jake opens one link. **Blocked by:** nothing.
- **Pass:** p95 frame interval ≤ 16.7 ms and ≤ 1% of frames over 33 ms, in both browsers, with bloom on.

### R12. Joules per token
- **Question:** How many joules does the board use per generated token, with and without glow and steering?
- **Why risky:** This is mostly logistics. The board's single USB-C port carries both 5 V power and adb data. Some inline meters break USB 2.0 data: AnandTech reported this for the POWER-Z KM003C (unverified; the article now redirects to AnandTech's forums). Idle draw has to be subtracted, and the NPU clock has to be pinned.
- **Cheapest experiment:** Put the meter between the Mac and the board and check `adb devices` through it. Log voltage and current at ≥ 10 samples/s during 5 runs of 200 tokens, plus 60 s idle. J/token = ∫P dt ÷ tokens. Fallback: power the board through the meter and drive it over the UART console with a 3.3 V USB-UART adapter.
- **Runs on:** the board; Jake does the plugging. **Cost:** a meter (~$30–80, unverified) and 30 minutes. **Blocked by:** T3.
- **Pass:** J/token reported with a 95% CI over 5 runs, both whole-board and with idle subtracted, with the NPU frequency recorded.

### R13. The atlas fits the board and the page
- **Question:** How big is the atlas the browser needs, and can the board serve it without slowing decode?
- **Why risky:** Labels, lenses, effects, ranges and layout come to about 600 B per neuron, or ~50 MB as JSON. Example snippets are bigger. FineWeb-Edu is ODC-By, so we must credit it.
- **Cheapest experiment:** Build the bundle from the R3 pilot and scale it to 86k. Use a binary format, and load examples lazily for each neuron.
- **Runs on:** cloud CPU, then a check on the board. **Cost:** free. **Blocked by:** R3.
- **Pass:** first load ≤ 10 MB compressed, hover data in ≤ 50 ms from the board, and decode tok/s unchanged while serving.

### R14. A Blender hero clip from real data
- **Question:** Can Blender render the map from a real recorded board session, frame-accurate and in reasonable time?
- **Why risky:** Blender has to animate 86k glowing points per frame, the render must finish in reasonable time on the Mac, and the clip must use the live UI's data mapping.
- **Cheapest experiment:** Export the layout and 10 s of recorded frames to `.npz`. Write a bpy script (Blender's Python API) with Geometry Nodes, and render a 2-second 1080p60 test with Eevee (Blender's real-time renderer) on the Mac.
- **Runs on:** Jake's Mac, or a RunPod GPU if that's too slow. **Cost:** free to $2. **Blocked by:** T8 (recording) and R9 (layout).
- **Pass:** ≤ 5 s per frame at 1080p, with colours and sizes matching the channel table.

## Appendix A. Budget

**GPU arithmetic (atlas on the INT4 replica).** Assumptions:
- **Cost per token:** one token through the replica costs 2 FLOPs × (440.4M transformer weights + 101.9M trimmed LM head) ≈ **1.08 GFLOP**.
- **Steered passes are cheaper:** a steered teacher-forced pass only reruns from the pushed layer upward, about half the transformer on average, so 0.44 + 0.20 ≈ **0.64 GFLOP**.
- **Faithful matmuls cost 2×:** the chip never builds dequantized weights. Per 32-weight block it sums x·q in bf16 and applies the scale afterwards (T5, `MixedQuantMatMulPattern.cpp`). A GPU copy of that kernel needs per-block partial sums, which we estimate at **2×** a plain bf16 matmul. T5 measured plain bf16 weights within cosine 0.999 of the kernel, so R3 can test whether the cheaper version changes the survivors.
- **Throughput:** an RTX 4090 has about 165 TFLOPS of dense bf16 peak (secondary sources, unverified). ## Appendix B. Probes run for this map

**Setup:** cloud sandbox (aarch64, 4 cores, 8 GB), Python 3.12, torch 2.14.1 (CPU), transformers 5.20.2, onnx 1.23.2, onnxruntime 1.31.0.
- **Models:** `Qwen/Qwen3-0.6B` @ `c1899de` and `Synaptics/Qwen3-0.6B-GPTQ-int4-torq` @ `f0e2fc9`. The `gptq/model.safetensors` SHA-256 `d98cbc01…` matches the LFS pointer.
- **INT4 replica:** all 196 linear layers plus the LM head come from GPTQ as `(q − zp) × trunc_bf16(scale)` in fp32 (Synaptics' `dequantize_weight`), so compute stays fp32. This is the fake-quant setup of Synaptics' accuracy check (T5's `int4-fp32`), not T5's board kernel. Host embeddings are bf16, and the LM head is read on the 99,520-entry trimmed vocabulary.
- **Text:** FineWeb-Edu sample-10BT rows (offset 1000) and two chat turns (non-thinking template, greedy fp32 answers). Position 0 is dropped.
- **Scripts** stayed in the sandbox, because this map is the only file the rules allow.

**P1. Can onnxruntime run the deployed op pattern?** We built a tiny graph, `DequantizeLinear` (int4, block 32, axis 0) → `MatMul`, at opset 21.
- With bf16 activations and scales, it fails: `NOT_IMPLEMENTED: Could not find an implementation for DequantizeLinear(21)`.
- In fp32, the default optimizer fuses the pair into `MatMulNBits`, with a max relative error of 4.6e-3 against float64. With optimizations off, the error is 1.6e-6 (K = 1024, N = 3072).
- **So:** ORT can't run the exported bf16 graph on CPU as it is. If it ever serves as a reference, turn graph optimizations off. The PyTorch replica (T5) is the right tool.

**P2. fp32 vs INT4 replica** (484 teacher-forced positions):
- Per-layer cosine: 0.994 at L0, falling to 0.943 at L13–14, then 0.987 at L27; mean 0.966.
- Top-100 overlap: 0.92, falling to 0.77, then 0.87.
- Neurons whose per-token correlation with fp32 is below 0.9: up to 16% at L14, 20–22% at L24–26, and 42% at L27.
- Next token: top-1 82.4%, KL 0.133. Synaptics reports 85.4% and 0.107 on 288 positions.
- The median residual norm (the dose unit) is within 1.5% at every layer.
- T5 measured the same gap with the board's numerics on its 8 chat prompts (534 positions): cosine 0.991 at L0–3, falling to 0.944–0.945 at L20–27, and top-100 overlap 0.90 falling to 0.78.
- **So:** an fp32 atlas would misdescribe many of the board's neurons, while the dose unit transfers.

**P3. bf16 vs fp32, same weights:**
- Cosine ≥ 0.9997 and top-100 overlap ≥ 0.98, but top-1 is 98.35% (8 flips in 484).
- The flips have margins of 0.012–0.142 nats. Above a 0.25-nat margin (85.5% of positions), agreement is 100%.
- **So:** a 99% top-1 bar needs a replica closer to the chip than bf16 is to fp32.

**P4. RoPE angles rounded to bf16, nothing else** (fp32 model, 4 FineWeb-Edu texts × 250 tokens):

| Positions | Top-1 agreement | Worst-layer cosine |
|---|---|---|
| 1–63 | 99.6% | 0.9999 |
| 64–127 | 99.6% | 0.998 |
| 128–191 | 96.9% | 0.994 |
| 192–249 | 94.7% | 0.985 |

Synaptics' exporter computes Qwen3's rotary embedding inside the graph; its table-folding step is commented "No-op for Qwen3". So whether the angle is computed in bf16 has to be read from the converted ONNX (R2, F6). If it is, the replica must copy it.

**P5. Which null matches real neurons?** INT4 replica, layers 8 and 19. Each push moves the residual by 0.5 × the median residual norm, along one of four kinds of direction:
- a real neuron column;
- an isotropic Gaussian (equally likely in any direction), like Lyra's controls;
- a column-space mix `W_down r`;
- a real column with its coordinates shuffled.

We tested 32 units × 2 signs of each kind, on 6 contexts × 40 tokens. *Lift* is the mean log-prob rise of the 10 tokens chosen on 3 contexts, measured on the other 3. *AUC* is the chance that a random real push beats a random null push on KL; 0.5 means indistinguishable.

| Null | L8 KL median (AUC) | L8: real lift above null p95 | L19 KL median (AUC) | L19: real lift above null p95 |
|---|---|---|---|---|
| real neurons | 0.449 | — | 0.601 | — |
| isotropic | 0.386 (0.68) | 23% | 0.709 (0.33) | 14% |
| column space | 0.423 (0.55) | 25% | 0.582 (0.52) | 22% |
| shuffled coords | 0.389 (0.70) | 25% | 0.725 (0.31) | 20% |

`W_down`'s spectrum is flat: its effective rank (how many directions it really uses) is 742 of 1024, and the top 10 singular directions hold 5% of the energy. Logit-lens kurtosis (how peaked a direction's word scores are) barely differs (3.10–3.20 for real vs 3.08–3.09 for nulls), so weight-only screens won't find many neurons in these layers. Lift ÷ √KL separated worse than lift.

**So:** use the column-space null, and expect the atlas to be the tail. With only 64 samples per kind, read these as directions, not final numbers.

## Appendix D. Atlas recipe

1. **Replica.** T5's `int4_ref.py` in `npu` mode, plus whatever R2 adds (the RoPE dtypes and lookup tables of the converted graph), with a static 256-token context. The CPU reference is T5, and the GPU copy must match it (cosine ≥ 0.999).
2. **Activation pass.** 20M tokens, half FineWeb-Edu and half UltraChat, in the board's chat template, positions ≥ 1. For each neuron-pole it keeps:
   - the top-50 64-token excerpts, each from a single document;
   - activation quantiles, for brightness calibration;
   - 16k random positions, for the layout;
   - and, per layer, the median residual norm, which is the dose unit.
3. **Units and nulls.**
   - **Units:** all 86,016 neurons.
   - **Nulls:** 2,048 per layer, `u = W_down r / ‖W_down r‖` with r ~ N(0, I), i.e. random mixes of that layer's columns.
   - **Push:** every unit moves the residual by `dose × median_resid_norm(L)` along its direction, at every position. For a neuron, that is exactly `h[n] += dose × med / ‖W_down[:, n]‖`.
4. **Statistic (fixed in advance).** Teacher-forced on 16 contexts × 64 tokens (8 chat, 8 FineWeb-Edu), split into halves A and B.
   - For each sign at dose 0.5, compute Δ = log p_steered − log p_base over the trimmed vocabulary at every position.
   - Pick T = the 10 tokens with the highest mean Δ on A.
   - lift = the mean Δ of T on B, and S = the larger of the two signs' lifts. KL is recorded too.
5. **p-values and FDR.** p = (1 + the number of same-layer nulls with S ≥ S_n) ÷ 2,049 (Phipson & Smyth 2010). Run BH at q = 0.05 over all 86,016 (Benjamini & Hochberg 1995), and report BY as well (Benjamini & Yekutieli 2001).
6. **Labels** (survivors, one per significant pole).
   - **Input:** Claude sees the top 20 training-split excerpts, with activations as integers 0–10 as in Bills et al. It also sees the logit lens and steer lens, both on the trimmed vocabulary.
   - **Output:** a name, a one-line description and 10 concept words.
   - **Score:** a simulator guesses 0–10 per token on 10 held-out top-activating and 10 random excerpts, scored by Pearson r. Baselines: a shuffled label from the same layer, and a token lookup table.
7. **Effects** (survivors). On 4 held-out chat prompts × 5 sampled seeds × 64 tokens, at the test dose and at the safe maximum, measure:
   - KL(steered ‖ base) along the steered trajectory;
   - and concept-logprob lift: the log of the total probability on the label's concept tokens, steered minus base.

   We bootstrap 95% CIs over prompt-seed pairs, on prompts the labeller never saw.
8. **Cliff.** Teacher-forced KL at ±{0.25, 0.5, 1, 2, 4}. The cliff is the dose where KL crosses κ (fitted in R8), and the slider range is 80% of the cliff for each sign. Survivors are checked with sampled generations.
9. **Layout.** As in R9.

## Appendix F. Glossary

- **Teacher-forced:** both models get the same input tokens, so they're compared step by step and never drift apart.
- **Top-1 agreement:** how often both pick the same most likely next token.
- **Top-100 overlap:** the share of the 100 strongest neurons that two runs have in common.
- **INT4 / GPTQ:** weights stored as 4-bit integers; GPTQ is the method that picks them to lose the least accuracy.
- **Replica:** our PyTorch copy of the exact graph the chip runs.
- **bf16:** a 16-bit number format with about 2–3 significant digits.
- **Binding:** one input or output buffer handed to the NPU program.
- **FDR / Benjamini–Hochberg (BH):** a rule that caps the expected share of false finds (here 5%) when testing 86,016 neurons at once.
- **Empirical p-value:** the share of random controls that do at least as well as the neuron.
- **Null direction:** a random push of the same size, used as the control.
- **Column space of `W_down`:** directions the layer's neurons can write. Random mixes of its columns make fair controls.
- **Dose:** a push measured in units of that layer's median residual norm (the typical size of the model's running state).
- **KL:** how much the next-token distribution moves.
- **Concept-logprob lift:** how much more likely the label's words become.
- **Logit lens / steer lens:** the words a neuron pushes toward, read from the weights (logit) or by actually pushing it (steer).
- **Pole:** a neuron's positive or negative side. They can mean different things.
- **Coherence cliff:** the dose where text breaks.
- **Simulation score:** how well someone who reads only the label can predict the neuron on new text.
- **Roofline:** a speed estimate from bytes moved per token.
- **Pearson r:** correlation, from −1 to 1; 0 means no relation.
- **Bootstrap CI:** error bars from resampling the data many times.
- **nats:** units of log-probability. A 0.25-nat gap means the top token is about 1.3× as likely as the runner-up.
- **Cross-fitted lift:** pick the words a push raises most on some texts, then measure how much it raises them on other texts, so the pick can't flatter itself.
- **AUC:** the chance that a random real neuron beats a random control; 0.5 means no difference.
- **TSL:** three.js's shader language.
- **Bloom:** bright points glow into their surroundings.
- **UMAP:** a way to squash many dimensions into 2D while keeping neighbours close.
- **Co-activation:** neurons firing on the same tokens.
- **devfreq:** Linux's control for the NPU clock.
